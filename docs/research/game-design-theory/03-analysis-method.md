## 0. 这个流程要解决什么问题

### 0.1 目标与反目标

**【本次综合推断】目标：**

1. 把一份游戏设计文本（策划案、规则书、攻略、补丁说明）转化为**可追溯的规则事实条目**。
2. 对每一条，**显式记录**它属于哪一分析层、证据等级多高、是否真的能由图谱承载。
3. **不**产生体验结论、**不**产生伦理结论、**不**产生「设计得好不好」的判断。

**【本次综合推断】反目标（做这些就是失败）：**

- 把设计意图当成规则事实。
- 把 MDA 的 Aesthetics 词表当成玩家情绪的测量结果。
- 用「Petri 网能建模」当作设计论证。
- 把单个案例的做法写成普遍规律。
- 在没有原文出处时凭常识补全数值或概率。
- 把求解器的「未发现冲突」当成「设计正确」。

### 0.2 与既有文档的分工

**【本次综合推断】** 本文件集（`docs/research/game-design-theory/`）位于 LUDO-2 本体文档的**上一层**：

| 层 | 文档 | 回答的问题 |
| --- | --- | --- |
| 本体定义 | `docs/research/01-ontology-game-design-theory.md`（LUDO-2） | 有**哪些**标签与关系？ |
| **理论依据** | **本文件集** | 这些标签**为什么**要这样分？边界在哪？ |
| 抽取实现 | 抽取/路由管线的设计文档 | 如何从文本自动得到标签？ |

**【本次综合推断】** 三者的关系是：本文件集**论证** LUDO-2 的分类选择，并**声明**其不可越界之处；抽取实现**消费**这两份文档。本文件集**不**修改 LUDO-2，也**不**替代抽取规范。

## 1. 流程总览（七步）

**【本次综合推断】以下七步是本流程的核心。**

```text
输入：一份设计文本 + 来源元数据
  │
  ├─ S1 来源登记        ← 建立来源可信度等级与可追溯 ID
  ├─ S2 句子切分与候选识别  ← 找出"可能承载规则事实"的句子
  ├─ S3 三层归属判定      ← 规则事实 / 设计意图 / 玩家体验
  ├─ S4 规则事实抽取      ← 映射到 17 标签（或记为 uncovered）
  ├─ S5 证据与确定性标注   ← 原文片段 + certainty + [unverified]
  ├─ S6 可验证性筛选      ← 哪些能被求解器验证，哪些不能
  └─ S7 反例与边界审查    ← 是否存在"看起来是规则事实其实不是"
  │
输出：结构化的规则事实条目 + uncovered 条目 + 验证目标清单 + 边界记录
```text

### S1 来源登记

**目的：** 任何一条抽取结果都必须能回答「你从哪里读到的」。

**【本次综合推断】操作：**

1. 为每份输入分配稳定 ID（如 `src-001`）。
2. 记录来源类型，并按 `00` 第 4 节的可靠性顺序分级：一手规则文本 > 设计者陈述（有出处）> 同行评议文献 > 二手报道 > 社区/众包。**拒绝**无出处的「众所周知」。
3. **对网络来源额外检查污染。** 【事实】本次研究直接遇到两个实例：<https://gameontology.org/> 首页被商业推广内容注入；`boardgamestudies.info` 现已是无关垃圾站。因此**「域名正确」不等于「内容可信」**——必须人工确认页面内容与主题一致。
4. 记录访问时点的**具体 URL**（含路径），不是站点首页。

### S2 句子切分与候选识别

**目的：** 在文本中找到「可能承载规则事实」的最小单元。

**【本次综合推断】候选信号词（中文/英文）：**

- 数值与阈值：`每次`、`最多`、`至少`、`提升 N%`、`per`、`at most`
- 时机与条件：`当`、`如果`、`之后`、`期间`、`when`、`while`、`upon`
- 主体与角色：`玩家`、`对手`、`队长`、`player`、`team`
- 状态转换：`变为`、`恢复`、`重置`、`becomes`、`resets`
- 目标与胜负：`获胜`、`失败`、`得分`、`wins`、`scores`
- 显式不确定性：`约`、`大约`、`随机`、`约莫`、`may`、`chance`

**【本次综合推断】重要：信号词只用于**召回**，不用于判定。** 出现数值不代表是规则事实（可能是设计意图描述：「我们希望玩家感到 20% 的压力提升」），不出现数值也不代表不是（「吃豆人吃掉能量豆后幽灵逃跑」无数字但是规则事实，见案例 4）。

### S3 三层归属判定（本流程最关键的一步）

**目的：** 判定句子的归属层。这是 `00` 第 2.1 节三层区分在流程中的落点。

**【本次综合推断】判定规则（按顺序检查，命中即停）：**

| 检查 | 命中条件 | 归属 |
| --- | --- | --- |
| C1 | 句子描述**可判定真假的状态/条件/数值**，且不依赖任何人相信它 | **规则事实** |
| C2 | 句子描述**意图、希望、目标体验、设计理由**（「我们希望」「目的是」「为了」） | **设计意图** |
| C3 | 句子描述**感受、理解、印象、反应**（「玩家会觉得」「令人紧张」） | **玩家体验**（不可抽取） |
| C4 | 句子是**叙事/世界观**（角色背景、地名、历史） | **风味/叙事**（可抽取但非规则） |
| C5 | 以上都不是（愿景声明、市场定位、团队分工） | **非本图谱范围** |

**【本次综合推断】四条硬规则：**

- **R1** C2/C3 的句子**永远不能**升级为 C1，即使它们包含数字。
- **R2** 若一句话**同时**含规则与意图（真实策划案极常见），必须**拆分**为两条，分别归属。**不得**整体归为规则事实。
- **R3** 若无法判定，归 `uncovered` 并**记录原因**，不得猜测。
- **R4** C3 条目不进入图谱，但**保留**为独立的「体验主张」记录，用于后续实证研究对接（见第 5 节）。

### S4 规则事实抽取

**目的：** 把 C1 句子映射到 LudoGraph 的标签与关系。

**【本次综合推断】操作顺序：**

1. **先判粒度。** 是 `Action`（代理人做的动作）、`Rule`（条件→结果的约束）、`Condition`、`Goal`、`Attribute`、`Resource`、`Entity` 还是 `System`？
2. **再判关系。** `PERFORMED_BY`、`REQUIRES`、`MODIFIES_ATTRIBUTE`、`TARGETS`、`TRIGGERS` 等。
3. **若 17 个叶标签中无合适项**，记为 `uncovered`，并**必须**写明「缺少什么概念」。这些记录是本体演进的输入（与 LUDO-2 的 `uncovered` 机制一致）。
4. **不得**为了「放进图谱」而把概念降级。例如把「不放回抽样」（案例 7）硬塞进 `Attribute` 的 `probability` 限定是**错误**做法；正确做法是记 `uncovered`，理由「需要 `RandomProcess` 结构」。

### S5 证据与确定性标注

**【本次综合推断】每条抽取结果至少带四个字段：**

| 字段 | 含义 |
| --- | --- |
| `evidence_span` | **逐字原文片段**（不是转述） |
| `source_id` | 指向 S1 的来源与具体 URL |
| `layer` | 规则事实 / 设计意图 / 玩家体验 / 风味 / 非范围 |
| `certainty` | 高 / 中 / 低 / [unverified] |

**【本次综合推断】`certainty` 的判据：**

- **高：** 来自权威规则文本（如 FIDE 规则、万智牌 Comprehensive Rules），句子是陈述性的。
- **中：** 来自设计者访谈或同行评议文献，措辞清晰。
- **低：** 来自二手报道、社区分析、或措辞含糊。
- **[unverified]：** 无直接来源，或来源未能核验（**必须**在正文标注，不得静默省略）。

**【本次综合推断】一个必须遵守的禁令：** 不得为任何数值、概率、效应量「补全」一个看起来合理的数。缺就写缺。

### S6 可验证性筛选

**目的：** 区分「图谱能验证的」与「图谱不能验证的」。

**【本次综合推断】三类目标：**

| 类别 | 例子 | 需要的工具 |
| --- | --- | --- |
| **可判定性质** | 状态可达性、状态机冲突、死锁、胜负可达性、数值边界、依赖闭包 | 状态机/Petri 网/SMT 类求解器（`00` 的 E 类） |
| **可仿真性质** | 经济系统收敛、随机过程分布（在给定假设下） | 蒙特卡洛仿真（**给出样本，不给定理**） |
| **不可验证** | 体验、意义、伦理、设计优劣 | 实证研究 / 论证——**不是图谱任务** |

**【本次综合推断】三条纪律：**

- **V1** 求解器报告「未发现冲突」**只**意味着「在给定建模假设下未发现」，不意味着设计正确。仿真模型本身内嵌假设（案例 6：Wright 的「任何仿真都是假设集合」）。
- **V2** 随机过程验证需要**不放回**等结构语义；若 schema 不支持，验证结果**不可信**，应明确声明而非强行输出。
- **V3** 不可验证项目**不应**被包装成「已通过验证」。

### S7 反例与边界审查（自检清单）

**【本次综合推断】抽取完成后，逐条问：**

1. 这句话是否其实是**设计意图**被写成了陈述句？（对照 C2 词：希望/目的/为了/想让）
2. 这句话是否包含**数值但实际是意图**？（R1 的常见违反）
3. 这条规则**在实现中**可能与文本不一致吗？（案例 4：Pac-Man 的 Pinky 源于代码错误）
4. 这条规则是否**依赖于玩家策略/其他玩家**？（案例 7：metagame → 不是 L1 规则事实）
5. 这条规则是否**随版本变化**？是否记录了有效期？
6. 我是否**从规则推出了体验**？（对照 `00` 第 2.1 节的禁令）
7. 我是否**从单个案例泛化**了？
8. 我的来源**页面内容是否与主题一致**？（污染检查）
9. 有没有 `[unverified]` 被我**静默丢弃**？
10. 有没有条目我**为了凑齐**而强行映射到某个标签？

**【本次综合推断】** 第 10 条最重要：**`uncovered` 是正确的输出，不是失败。**

## 2. 工作示例 A：塔防策划案（完整走完七步）

**输入：** 一段虚构的塔防策划案文本。**【事实】说明：由于本次研究未获得公开的塔防策划案原文，本示例的输入文本是**为演示流程而构造的**，其结构参照真实策划案的常见写法。因此本示例演示的是**流程**，不是对某款具体游戏的断言。本示例的每一条都标注了它在演示中的角色。**

### 输入文本（构造）

> **§3 波次与敌人**
>
> 3.1 本关卡共 12 波。每波持续 30 秒，波次之间间隔 10 秒的准备阶段。
>
> 3.2 从第 5 波开始，所有敌人的移动速度提升 20%，此效果在后续所有波次中持续。
>
> 3.3 敌人从我方基地外的三条通道之一随机出现，三条通道的权重分别为 50%、30%、20%。同一敌人不会重复选择通道。
>
> 3.4 我们希望通过第 5 波的提速让玩家在中盘感受到明显的压力上升，营造"局势开始失控"的体验。
>
> 3.5 每一波中，被击毁的敌人有 15% 概率掉落一个能量核心，玩家可用能量核心升级防御塔。
>
> 3.6 玩家必须阻止敌人到达基地。若有 20 个敌人抵达基地，玩家失败。
>
> 3.7 本关卡的目标是让玩家在 25 分钟内获得一次完整的塔防体验。

### S1 来源登记

| 字段 | 值 |
| --- | --- |
| `source_id` | `src-demo-001` |
| 来源类型 | **构造文本**（演示用），非真实来源 |
| 可靠性等级 | 不适用（演示） |
| URL | 无 |
| 污染检查 | 不适用 |

**【本次综合推断】诚实说明：** 本示例的输入**没有真实来源**，因此**全部**抽取结果的 `certainty` 不能被评为「高」。这本身是 S1 的一个演示：**来源等级会向下游传导**。

### S2 候选识别

| 句 | 信号 | 候选 |
| --- | --- | --- |
| 3.1 | 数值、时机 | 波次数、每波时长、间隔 |
| 3.2 | 数值、条件（从第 5 波）、转变（提升 20%） | 难度缩放 |
| 3.3 | 随机、权重、可能性 | 随机过程 |
| 3.4 | **意图词（希望通过 / 营造 / 感受到）** | **设计意图 → 不进规则** |
| 3.5 | 概率、条件、资源 | 掉落 + 资源 |
| 3.6 | 目标、失败条件、阈值 | 胜负条件 |
| 3.7 | **意图词（目标是让 / 体验）** | **设计意图 → 不进规则** |

### S3 三层归属判定

**【本次综合推断】逐句判定：**

| 句 | 归属 | 理由 |
| --- | --- | --- |
| 3.1 | **规则事实** | 可判定真假的状态/时长/数量，不依赖任何人相信 |
| 3.2 | **规则事实** | 条件（波次 > 5）→ 结果（速度 +20%），可判定 |
| 3.3 | **规则事实**（但**不完整**） | 「随机 + 权重」可判定；「不会重复选择通道」**语义不明**——是「不放回」还是「不连续重复」？→ 触发 R3，记 `uncovered` |
| 3.4 | **设计意图** | 「希望」「感受到」= C2；**含数字冲击但无数字**，仍是意图。**不进规则图谱** |
| 3.5 | **规则事实** | 概率 15% + 条件 + 资源 |
| 3.6 | **规则事实** | 失败条件与阈值 |
| 3.7 | **设计意图** | 「目标是让」= C2；**且包含时间数值 25 分钟，但不属规则**（是意图描述） |

**【本次综合推断】关键演示点：** 3.7 含一个突出的数字（25 分钟），是最容易被误抽为规则事实的句子。**R1 在此生效：它是意图，不是规则。**

### S4 规则事实抽取

**【本次综合推断】结果（17 标签下的映射尝试）：**

| 句 | 标签 | 关系 | 说明 |
| --- | --- | --- | --- |
| 3.1 | `Level`（关卡）+ `TimeFrame`（缺失） | `HAS_PHASE`（可能缺失） | 12 波、30 秒、10 秒准备 → **"波次"无对应叶标签** |
| 3.2 | `Attribute`（速度）+ `Rule` | `MODIFIES_ATTRIBUTE`(increase) + `TRIGGERS` | 条件「波次序号 > 5」→ 但**"波次序号"无处安放** |
| 3.3 | `Attribute`（权重） | — | **权重可存，结构性语义不可存** |
| 3.5 | `Resource`（能量核心）+ `Rule`（掉落）+ `Action`（升级） | `DROPS`(可能缺失) + `CONSUMES` | 概率 15% 可存为 `probability` |
| 3.6 | `Goal`（胜利/失败）+ `Condition` + `Entity`（敌人、基地） | `REQUIRES` + `TARGETS` | 阈值 20 — **但"基地"是 Entity 还是 Attribute?** |

**【本次综合推断】`uncovered` 清单（这是本示例最重要的输出）：**

| # | 缺少的概念 | 为什么现有标签不够 | 对应 LUDO-2 建议 |
| --- | --- | --- | --- |
| U1 | **`Wave` / 玩法分段** | 「波次」既不是 `Level` 也不是 `TimeFrame`；它是一个**带序号的重复单元**，有开始、有内容、有间隔 | 与 `Cycle` 建议相关 |
| U2 | **`Phase`（准备阶段）** | 「准备阶段」是一个**无战斗的时间段**，与「波次」互斥，属状态机语义 | `Phase` 建议 |
| U3 | **`TimeFrame`（30 秒 / 10 秒）** | 30 秒是 real-world time，10 秒准备是 coordination time——**同一句里两种时间** | `TimeFrame` 建议（Zagal & Mateas 四时间） |
| U4 | **`RandomProcess` 结构语义** | 「不会重复选择通道」在 `probability` 限定下**无法表达**（不放回？不连续重复？） | `RandomProcess` / `ChanceOutcome` 建议 |
| U5 | **有序计数器** | 「第 5 波」「波次序号」需要一个**可比较的序号**，不是 `Attribute` 值 | 与 `Cycle`/`Phase` 建议相关 |
| U6 | **全局设计定位** | 3.7 的「让玩家获得完整塔防体验」是**整关的设计定位**，不属于任何单条 claim | 无建议（真实的 schema 空白） |

**【本次综合推断】结论：6 条 `uncovered` 对 5 条可映射。** 这个比例（多于一半的信息无法映射）**不是流程失败**，而是流程**成功暴露了本体的缺口**。这正是 LUDO-2 的 `uncovered` 机制要捕捉的东西。

### S5 证据与确定性标注

**【本次综合推断】示范两条：**

```yaml
- id: claim-demo-001
  layer: 规则事实
  evidence_span: "本关卡共 12 波。每波持续 30 秒，波次之间间隔 10 秒的准备阶段。"
  source_id: src-demo-001
  certainty: 低          # 构造文本，无真实来源
  tags: [Level]
  relations: []
  uncovered: [U1, U2, U3]

- id: claim-demo-002
  layer: 设计意图        # 明确标为意图
  evidence_span: "我们希望通过第 5 波的提速让玩家在中盘感受到明显的压力上升，营造"局势开始失控"的体验。"
  source_id: src-demo-001
  certainty: 低
  intent_target: 压力上升 / 失控感
  intent_strength: 明确   # 对应 02 §11.1 的控制度谱
  rationale: 案例 10 的强意图控制 vs 案例 6 的弱意图控制谱系
```yaml

**【本次综合推断】注意 claim-demo-002 的关键设计：** 它**被保留**（不是被丢弃），但 `layer` 明确是 `设计意图`。这使后续实证研究可以拿它去检验「玩家是否真的感到压力上升」——这正是 `01` 第 4.2 节 Anderson et al.（2019）那种检验的输入形态。

### S6 可验证性筛选

**【本次综合推断】针对本示例：**

| 验证目标 | 类别 | 可行性 | 说明 |
| --- | --- | --- | --- |
| 是否可能出现「无敌人可打」的波次（波次与生成器不同步） | 可判定 | 中 | 需要 `Wave`/`Phase` 建模（当前缺失，**无法验证**） |
| 「20 个敌人到达即失败」是否可达 | 可判定 | 高 | 阈值 + 计数，标准可达性 |
| 「从第 5 波起速度 +20%」是否与波次终止条件冲突 | 可判定 | 中 | 需要 U5（有序计数器） |
| 能量核心经济是否收敛（不会无限升级） | **可仿真** | 低 | 需要成本曲线——**文本未给出**，标 `[unverified]`，**不得**自行假设 |
| 玩家是否感到压力上升 | **不可验证** | — | 需实证；图谱任务范围外 |

**【本次综合推断】两个纪律演示：**

- **V1 生效：** 「未发现波次冲突」在 `Wave` 建模缺失时**无意义**。因此第一条的目标应直接标为「当前无法验证」，而不是「已验证通过」。
- **「不得自行假设」生效：** 成本曲线缺失，**不得**补一个「通常是指数曲线」——那是凭空发明需求。

### S7 边界审查

**【本次综合推断】逐条过清单：**

| # | 检查项 | 结果 |
| --- | --- | --- |
| 1 | 意图被写成陈述句？ | **命中**：3.7「本关卡的目标是……完整的塔防体验」若无 S3 的 C2 检查，极易被抽为 `Goal` 实体。已正确归为意图。 |
| 2 | 数值但实为意图？ | **命中**：3.7 的「25 分钟」。已按 R1 处理。 |
| 3 | 实现可能与文本不符？ | 无法检查（构造文本）。**标注为流程的已知局限。** |
| 4 | 依赖玩家策略/其他玩家？ | 不适用（单机塔防）。 |
| 5 | 随版本变化？ | 「第 5 波 +20%」是典型的**平衡改动高频对象**。应带版本/有效期。 |
| 6 | 从规则推出体验？ | **未命中**（claim-demo-002 被明确隔离为意图）。 |
| 7 | 从单案例泛化？ | **未命中**（本示例不产出任何普遍结论）。 |
| 8 | 来源污染？ | 不适用（构造文本）。 |
| 9 | `[unverified]` 被静默丢弃？ | **未命中**（成本曲线缺失被显式记录）。 |
| 10 | 为凑齐而强行映射？ | **未命中**（产出 6 条 `uncovered` 而非硬塞）。 |

**【本次综合推断】S7 的价值在于第 1、2 条在本示例中**都命中了**。这说明「意图与含数字的意图被误抽为规则」不是罕见的边界情况，而是**高频失效模式**。

## 3. 工作示例 B：从案例 4（Pac-Man）走流程（真实来源版）

**【事实】本示例的输入是真实的一手文本**（Pac-Man Dossier），用于对比示例 A（构造）与真实来源在证据等级上的差别。

### 输入文本（逐字）

来源：Jamey Pittman, "The Pac-Man Dossier"。〔<https://www.gamedeveloper.com/design/the-pac-man-dossier>，本次核验〕

- 「Each of the ghosts was given an unique personality and character.」
- 「The ghosts have three mutually exclusive modes: chase, scatter, and frightened.」
- 「Pinky's target tile is four game tiles ahead of Pac-Man... if Pac-Man is moving up, [it] is four tiles up and four tiles left... a subtle error in the logic code.」
- 「Clyde... targets Pac-Man when he is more than eight tiles away... switches to his scatter-mode target when he gets close to him.」

### S1–S3

| 字段 | 值 |
| --- | --- |
| `source_id` | `src-pacdossier` |
| 来源类型 | 二手但**高度技术性、可核验**的关卡/机制分析（原作者为逆向分析者） |
| 可靠性 | **中**——非官方规则文本，但机制陈述可被代码验证 |
| URL | 具体文章路径（非首页） |
| 污染检查 | 通过（页面内容与主题一致） |

**【本次综合推断】S3 判定：**

- 「Each of the ghosts was given an unique personality and character」→ **设计意图/设计陈述**（C2）。**注意：这句话极易被误抽为规则事实**——它用了陈述句，且听起来像系统属性。**但「性格」不是可判定的状态/条件/数值**。
- 「three mutually exclusive modes」→ **规则事实**（互斥性是状态机性质，可判定）。
- 「target tile is four game tiles ahead」→ **规则事实**（可判定）。
- 「a subtle error in the logic code」→ **实现事实**（第三方类别！不是规则事实，也不是设计意图）。

**【本次综合推断】这暴露了一个 S3 未覆盖的归属层：`实现事实`。** 示例 B 因此给流程增加一条：

| 检查 | 命中条件 | 归属 |
| --- | --- | --- |
| C6 | 句子描述**代码/实现的实际行为**，可能与设计文档不符 | **实现事实**（第四类，独立标注） |

**【本次综合推断】这是示例 B 对流程的实际贡献：** 真实来源比构造文本**多出一种需要区分的层**。流程因此修订，而不是硬把「代码错误」塞进已有三类。

### S4 抽取结果

| 句 | 标签 | 关系 | uncovered |
| --- | --- | --- | --- |
| 三模式互斥 | `State` × 3 + 状态机 | `TRANSITIONS_TO` | 无（LUDO-2 的 `State`/`StateTransition` 覆盖良好） |
| Blinky 目标 = 当前格 | `Rule` + `TARGETS` | `TARGETS` | 无 |
| Pinky 目标 = 前方 4 格（含向上特例） | `Rule` + `TARGETS` | `TARGETS` | 无 |
| Inky 目标 = 加倍法 | `Rule` + `TARGETS` | `TARGETS` | **U7：多主体依赖的目标计算**（Inky 的目标依赖 Pac-Man **与 Blinky** 两者的位置；`TARGETS` 单边关系不足以表达） |
| Clyde 八格阈值切换 | `Rule` + `Condition` + `TARGETS` | `TARGETS` | 无 |

**【本次综合推断】新发现的缺口 U7** 是示例 B 的第二个实际产出：真实规则比构造文本更早暴露「关系表达力不足」。

### S6 可验证性

| 目标 | 类别 | 可行性 |
| --- | --- | --- |
| 三种模式是否真的互斥（不存在两模式同时激活的状态） | 可判定 | **高**——这是状态机冲突检测的教科书用例 |
| Clyde 的八格阈值是否与 scatter 计时器产生不一致行为 | 可判定 | 中（需要计时器与阈值联合建模） |
| 玩家是否感知到幽灵「性格」 | **不可验证** | — |

**【本次综合推断】第一行是 `00` 中 E 类工具**最有价值**的应用场景**：它不是设计理论，但它能抓出真实的状态机 bug 类别。这符合 `01` 第 6.2 节第 3 条的立场——形式工具是验证层的正确工具，只是不是设计理论。

### S7 审查

| # | 检查 | 结果 |
| --- | --- | --- |
| 1 | 意图被写成陈述句？ | **命中两次**：「unique personality and character」（意图）、「paku paku」（设计意图/命名自述） |
| 3 | 实现可能与文本不符？ | **命中**：Pinky 的代码错误——本例的核心发现 |
| 9 | `[unverified]` 静默丢弃？ | **未命中**：见 `02` 案例 4 中关于「吸引女性玩家」意图的 [unverified] 标注 |

## 4. 两个示例的对比与流程修订

**【本次综合推断】对比表：**

| 维度 | 示例 A（构造塔防） | 示例 B（Pac-Man 真实来源） |
| --- | --- | --- |
| 来源可靠性 | 不适用（构造） | 中（可核验的二手技术分析） |
| 可映射条目 | 5 | 5 |
| `uncovered` 条目 | 6（U1–U6） | 1（U7） |
| 新发现的归属层 | 无 | **C6 实现事实** |
| 主要失效模式 | 意图含数值 → 误抽为规则 | 设计陈述（「性格」）→ 误抽为规则 |
| 可验证性 | 低（关键概念缺失） | 高（状态机互斥、可达性） |

**【本次综合推断】三条结论：**

1. **`uncovered` 比例高不是失败信号。** 示例 A 的 6:5 反映了构造文本的**概念密度**（一个波次系统同时触发时间、阶段、循环、随机四个缺口），而示例 B 的 1:5 反映了 LUDO-2 的 `State`/`Rule` 在单机街机领域覆盖良好。**本体缺口是类型依赖的。**
2. **真实来源会暴露流程未预见的类别。** C6（实现事实）只在示例 B 出现。这说明 S3 的判定表**必须**保持可扩展，而不是一个封闭枚举。
3. **「设计陈述句」是最危险的误抽源。** 两个示例都命中了这个模式：「每个幽灵有独特个性」「本关卡的目标是让玩家获得完整体验」。二者都是**陈述句形式的意图/评价**，且都**不含**「我们希望」这类显式信号词。**因此 C2 不能只依赖关键词匹配**——必须依赖「这个句子是否描述可判定的状态/数值」这一语义检查。

**【本次综合推断】由此对 S3 的修订建议：** 把判定顺序改为**先问 C1（可判定性），再由后续检查接管**。「是不是可判定真假的状态/条件/数值」比「有没有意图词」更可靠。

## 6. 流程的已知局限

**【本次综合推断】六条局限，均未被本流程解决：**

1. **无法处理图文混合。** 真实策划案含大量截图、流程图、UI 稿。本流程只处理文本。
2. **无法处理表格与配置表。** 数值常以 Excel/CSV 给出，其中「列的含义」依赖表头约定而非自然语言。这需要独立的表结构理解路径。
3. **无法判定文本↔实现一致性。** 如案例 4 的代码错误。这需要代码分析，不是文本分析。
4. **「可判定性」判定本身可能出错。** S3 的 C1 依赖对文本语义的判断；如果策划文本写得含糊（案例 9 的「不会重复选择通道」），流程只能记 `uncovered`，不能消解歧义。
5. **无法处理跨文档一致性。** 若同一机制在两份策划文档中描述不同，本流程**不**提供冲突解决规则——只能各自抽取并标记，冲突须人工处理。
6. **没有实证校准。** 本流程不产出、也不验证任何关于玩家体验的主张（P2 只是**保存**意图以待他人检验）。

**【本次综合推断】关于第 6 条的重要补充：** 这不是缺陷而是**范围界定**。`01` 第 5.3 节已经说明：机制与体验的经验联系是小效应、异质的；因此**任何**声称「本流程能预测体验」的说法都是错的。本流程的目标是产出**可追溯的规则事实**，不是产出体验预测。

---

## 7. 何时**不**该使用本流程

**【本次综合推断】四种情况：**

1. **目标是评估设计优劣。** 本流程不产生价值判断。需要经验标准与设计评审，不是抽取。
2. **目标是解释文化意义。** 见案例 2（Monopoly）与案例 5（文明）。需要批评理论，不是抽取。
3. **目标是研究玩家行为。** 需要实证方法（问卷、日志、实验），本流程产出的是输入而非结论。
4. **输入是纯叙事文本。** 若文本描述的是世界观与剧情（案例 4 的「paku paku」命名来源、角色背景），其规则事实密度极低，抽取收益有限。
