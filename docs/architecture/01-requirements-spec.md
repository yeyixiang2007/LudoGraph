# 需求规格说明（MVP 阶段）

- **文档性质：** 设计草案（v1 draft）。本文件定义 LudoGraph MVP 阶段要做什么、不做什么、以及每一条要求如何被验证。
- **上游依据：** 仓库 `README.md`、`docs/LudoGraph 图谱数据模型设计.md`、`docs/research/` 下的调研与文献综述。
- **写作纪律：** 凡本文档给出的性能或质量数字，若没有本仓库可复现的实测证据，一律标记为**待实测目标（target, unverified）**，不得读作已达成能力。
- **不在本文档范围内：** 代码实现、具体库版本锁定、商业交付承诺、论文 novelty 声明。

## 1. 背景与问题陈述

### 1.1 问题

现代服务型游戏的规则集合（经济、掉落、任务链、状态机、技能冷却、数值成长、限时活动、交叉依赖）在复杂度上已接近中型软件系统，而其权威来源常常不是可执行代码，而是自然语言策划文档、Excel 配置表、流程图与口头约定。传统 QA 在「发现已知问题」上有效，但在「证明未知规则组合不违反约束」上根本受限；形式化验证在原则上能填补该缺口，但它要求一个可计算、无歧义、结构化的形式模型，而策划文档恰恰缺乏这种模型。

问题因此被拆为三个必须串联、且**不可相互替代**的子问题：

| 子问题 | 提问 | 失败模式 |
| --- | --- | --- |
| **抽取** | 如何从半结构化文本抽出**原文明确说出**的规则事实，而不是让模型补写一个「合理的世界」？ | 模型补写因果/数值/身份；幻觉被当作事实入库 |
| **表示** | 用什么本体、存储模型与查询接口承载这些事实，使它们可审计且可机器查询？ | 丢失限定词与来源；冲突被覆盖合并；无法回指原文 |
| **验证** | 如何把事实编译为可判定、规模可控的约束问题，并正确解释 `sat`/`unsat`/`unknown`？ | 求解器对错误编码的模型给出**完全正确的错误答案** |

### 1.2 三个必须分离的层次（本项目的核心不变式）

本项目最重要的方法论约束是一条跨层不变式，它同时约束抽取、表示与验证：

| 层次 | 保证什么 | **不**保证什么 | 典型误用 |
| --- | --- | --- | --- |
| **格式层** | JSON/Schema/语法合法 | 字段语义 | 「structured output 成功 = 抽取成功」 |
| **本体层** | 标签/谓词/domain-range 合法 | 事实是否存在于文本 | 「domain-range 合法 = 关系为真」 |
| **事实层** | 断言被原文 span 支持 | 推断是否正确、模型是否编码正确 | 「quote 相关 = quote 蕴含 claim」 |

**每层的形式保证都只覆盖该层，且都不覆盖下一层的语义。** 本规格的所有可验证要求都锚定在这条不变式上：任何需求若无法说明它验证的是哪一层，即为规格缺陷。

### 1.3 目标检测类别（MVP 三项）

| 编号 | 类别 | 定义 | 主要验证手段 |
| --- | --- | --- | --- |
| **D1** | 经济死锁 | 资源循环依赖、无法达成的产出/消耗闭环、库存非负不可维持 | 线性不变量 + LP 可行性 + 有界 SMT |
| **D2** | 状态机冲突 | 互斥状态同时成立、状态转换不可达 | one-hot 编码 + 有界 BMC + 图可达性 |
| **D3** | 数值极值 | 属性越界、数值爆炸或归零 | 区间抽象（过近似快筛）+ 有界 SMT 精化 |

**关键纪律：** 这三类**不是**三个同质的「bug 类型」。D1 的量词结构主要是 `∃`（存在一条可执行路径导致违规）与「净产出流是否存在」两种不同性质；D2 混合可达性（`∃` 路径）与不变量（`∀` 状态）；D3 依赖数值域语义（`Int` vs `BitVec(w)` vs `Real`）。把三者统一压成「是否存在死锁」会丢失语义——这一条是需求，不是建议。

## 2. 功能需求

编号采用 `FR-<模块>-<序号>`。模块缩写：`EX` 抽取、`GX` 图谱/契约、`QR` 查询路由、`VF` 验证、`VS` 版本。

### 2.1 抽取层（EX）

| 编号 | 需求 | 可验证性 |
| --- | --- | --- |
| **FR-EX-1** | 系统须接受一份策划文档切分出的 chunk 作为抽取输入，并输出符合抽取合同的顶层结构：`ontology_version`、`scope`、`status`、`nodes`、`claims`、`uncovered`。 | JSON Schema 校验通过/失败可判定 |
| **FR-EX-2** | `nodes` 中的每个节点须使用**具体的 canonical 叶子标签**（17 个之一，见 `05-graph-schema-design.md`），不得输出上位标签 `Entity`/`Mechanic` 等作为节点标签。 | 白名单校验器拒绝；违反率目标为 0 |
| **FR-EX-3** | `claims` 的 `predicate` 须在白名单内，且 subject/object 的端点类型须满足该谓词的 domain/range。 | 校验器拒绝；domain/range 违反率目标为 0 |
| **FR-EX-4** | 每条 claim 须携带 `qualifiers`（条件、数值、时序等限定）、`certainty`、`evidence`；缺失任一项即为不合法输出。 | 结构校验器拒绝 |
| **FR-EX-5** | `evidence.quote` 须是当前输入 chunk 的**连续原文子串**，不得改写、拼接或引用 chunk 外材料。 | 服务端确定性检查 `quote == chunk[start:end]`；目标覆盖率 100%（硬门槛） |
| **FR-EX-6** | `qualifiers.quantity` 须保留原文 `raw`；仅在可明确解析时才附 `value` 与原文 `unit`。禁止隐式单位换算与归一化覆盖原文。 | 校验器检查 `raw` 非空；抽查 `value` 与 `raw` 一致性 |
| **FR-EX-7** | `qualifiers.cycle_text` 须保留结算周期原文，**不得**自行换算为 tick、回合或工作日。 | 校验器检查是否存在未声明的换算字段 |
| **FR-EX-8** | `certainty` 取值须为 `explicit`/`possible`/`planned`/`negated` 四态之一，描述**原文语气**而非模型置信度。 | 枚举校验 |
| **FR-EX-9** | 当文本有规则意义但当前不能可靠表示时，系统须写入 `uncovered`（含原文片段、原因代码、证据），而非强行归类或丢弃。 | `uncovered` 项结构校验；拒绝能力指标见 §5 |
| **FR-EX-10** | 系统**不得**因名字相同而自动跨 chunk、跨文档、跨游戏合并节点。合并只能经独立的 `entity_link` 流程 + 人工审核。 | MVP 阶段 `entity_link` 不在范围内，需以「未实现」状态显式暴露 |
| **FR-EX-11** | 原文互相矛盾时，系统须保留各自的 claim 与来源，不在抽取阶段裁决。 | 冲突 claim 并存测试 |

### 2.2 图谱契约与存储（GX）

| 编号 | 需求 | 可验证性 |
| --- | --- | --- |
| **FR-GX-1** | 抽取数据合同须与物理数据库解耦：同一份抽取输出须能被投影为「关系属性」与「独立 `Assertion` 节点」两种形态，且语义不变。 | 两种投影对同一查询给出一致结果 |
| **FR-GX-2** | 投影后每条断言须保留 `qualifiers`、`certainty`、证据、`source`/`chunk_id`、命名空间与 `ontology_version`。 | 投影往返（round-trip）测试 |
| **FR-GX-3** | 须为每条断言生成**确定性持久 ID**：对规范化 tuple `(game_id, system_id, source_id, chunk_id, 局部 claim id 或 source span, revision)` 做 SHA-256。 | 同一输入重跑 ID 稳定；不同来源不碰撞 |
| **FR-GX-4** | 断言的生命周期状态 `status`（`active`/`deprecated`/`rejected`）须与 `certainty` 在结构上分离存储。 | 二者可独立变更而不互相污染 |
| **FR-GX-5** | 不同来源的冲突事实须作为不同断言保存，修订通过新增版本 + `supersedes` 表达，不得原地覆盖历史。 | 修订后旧断言仍可查询；审计链完整 |
| **FR-GX-6** | 图谱 schema 须以单一权威来源驱动：本体文档、校验器白名单、数据库约束三者由同一份机器可读 schema 生成。 | schema 漂移检查（见 §5 CI） |

### 2.3 查询路由（QR）

| 编号 | 需求 | 可验证性 |
| --- | --- | --- |
| **FR-QR-1** | 系统须把自然语言问题先路由为**结构化意图 + 槽位**，再编译为目标图方言查询；不得让模型直接端到端吐 Cypher 字符串作为唯一路径。 | 路由输出可枚举、可单测 |
| **FR-QR-2** | 编译前须进行**后端能力探测**：目标方言不支持的特性须显式拒绝并给出降级路径，而非生成不可执行查询。 | 方言能力矩阵测试 |
| **FR-QR-3** | 查询结果须携带从「查询 → 断言 → 来源 chunk → 原文 span」的完整回指链。 | 回指链完整性测试 |
| **FR-QR-4** | 高频模板/已编译查询须走快路径（缓存/规则/模板），不得每次都经过完整冷路径。 | 快路径命中可计数、可测试 |
| **FR-QR-5** | 当自然语言问题超出当前本体可表达范围时，系统须返回明确的「不可回答」信号及原因，而不是返回一个语义漂移的近似查询。 | 拒绝行为测试 |

### 2.4 形式化验证（VF）

| 编号 | 需求 | 可验证性 |
| --- | --- | --- |
| **FR-VF-1** | 每条形式化约束须可回指规则 claim 与原证据（SMT assertion → 图断言 → 原文 span）。 | 回映射测试；目标回指率 100%（硬门槛） |
| **FR-VF-2** | 系统须对每个验证任务输出**多结果协议**：`proved` / `counterexample` / `bounded-no-counterexample` / `unknown` / `not-modeled`（可选 `spurious-counterexample`）。不得把 `unknown` 当作「通过」。 | 结果枚举校验；统计各类占比 |
| **FR-VF-3** | `bounded-no-counterexample` 须显式携带边界参数 `k`，且不得被表述为全局安全。 | 输出格式强制 `k` 字段；文档/接口层面禁止「安全」措辞 |
| **FR-VF-4** | 数值属性须按运行时语义选择 `Int` / `Real` / `BitVec(w)`；当目标系统使用 `w` 位整数时，须按位向量运算验证，不得以无界 `Int` 推断机器溢出。 | 编码选择可审计；位溢出单独测试用例 |
| **FR-VF-5** | D1 经济死锁须区分「存在净产出流」（LP 可行性）与「存在合法可执行操作序列」（库存非负 + 前置条件 + 顺序），后者才是死锁的真正对象。 | 两个性质分别有可复现的通过/失败用例 |
| **FR-VF-6** | 禁止把 SCC/资源依赖环本身当作死锁证明；禁止把「玩家可主动等待」判为死锁。 | 反例集中须包含「有环但无死锁」用例 |
| **FR-VF-7** | D2 多状态机同步时，须为共享事件、锁、优先级与更新原子性建立**显式联合转移**；不得默认隐式并发。 | 联合转移存在性检查；竞争/遗漏用例 |
| **FR-VF-8** | 求解器须以无共享 worker pool 运行：每个 worker 持有私有 Context/solver，任务间不跨 context 传递 AST，worker 间以可序列化的 SMT-LIB 或项目 IR 传输。 | 并发压力测试；无跨 context 对象泄漏 |
| **FR-VF-9** | 语义不明（缺概率/单位/缺省/优先级/例外语义）的 claim **不可**强行编码进模型，须返回 `not-modeled` 或 `unknown` 并说明缺失字段。 | 缺失字段用例须进入非 `proved` 分支 |
| **FR-VF-10** | 编译须采用保守三分：证明保持的过近似（假阳性可接受）、反例保持的欠近似（找不到反例不代表安全）、未决定/待澄清。三分须在输出中可区分。 | 编译结果类型枚举 |

### 2.5 版本演化（VS）

| 编号 | 需求 | 可验证性 |
| --- | --- | --- |
| **FR-VS-1** | 系统须能保存规则快照并为同一规则系统生成可比较的版本。 | 快照往返测试 |
| **FR-VS-2** | 版本变化后，须能判定并报告哪些既有结论仍然保持、哪些反例已失效、哪些需要重跑。 | 版本回归报告可复核 |
| **FR-VS-3** | 「版本兼容」须被显式定义为至少三种不同性质：「资源价值不下降」「目标仍可达」「旧存档可继续」，且三者**分别**报告。 | 三种性质有独立用例 |
| **FR-VS-4** | MVP 阶段须提供版本 diff 与影响路径的最小能力（哪些断言被 supersede、哪些查询受影响）。 | diff 输出可复核 |

> **说明：** FR-VS-2/3 属于 MVP 的**最小可用**版本（报告 + 分支验证），完整的「精化保持与反例迁移定理」属于后续研究阶段，不在本 MVP 交付的证明义务内。

## 3. 非功能需求

### 3.1 正确性与保守性（最高优先级）

| 编号 | 需求 | 依据 |
| --- | --- | --- |
| **NFR-1** | 保守拒绝优于虚假确认：当证据不足时，系统须输出 `uncovered`/`not-modeled`/`unknown`，而非构造一个看似合理的结论。 | 抽取、验证层共享同一认识论立场 |
| **NFR-2** | 冲突不覆盖：任何来源冲突并存，交后续审核。 | 保留可审计历史 |
| **NFR-3** | 形式合法不得被报告为语义正确。文档、接口文案与指标命名均须遵守三层分离。 | §1.2 |
| **NFR-4** | 「未提及」不得被编译为「禁止」（开放世界/闭世界假设须显式声明为编译期开关）。 | 已知失败模式清单 |

### 3.2 性能（**全部为待实测目标**）

**先声明纪律：** 本项目**不承诺**「毫秒级端到端验证」。公开可核验的证据只支持以下结论——「毫秒级」适用于缓存、规则、模板与已编译查询这类快路径，不适用于任意自然语言到 Cypher 的完整冷路径；SMT 的运行时间没有可按约束条数通用推导的界限。因此性能需求采用**分层、分场景**表述：

| 编号 | 场景 | 目标（target, unverified） |
| --- | --- | --- |
| **NFR-P1** | 高频模板/缓存命中查询 | P50 ≤ 10ms，P95 ≤ 30ms |
| **NFR-P2** | 常驻小模型意图路由 | P50 ≤ 50ms，P95 ≤ 150ms |
| **NFR-P3** | 动态 NL2Cypher 冷路径 | P50 ≤ 300ms，P95 ≤ 1s |
| **NFR-P4** | 三类检查的求解器侧 | 须报告按理论片段（`QF_LIA`/`QF_BV`/CHC）分层、按状态规模的 P50/P95/P99 与内存；**不设统一数字目标**，以本机实测基线代替 |

**硬性要求：** 任何性能声明必须附「输入规模 + 硬件 + 冷/热 + 并发数 + 理论片段」四要素；缺少任一要素的数字不得写入设计文档、README 或对外材料。

### 3.3 可审计性与可追溯性

| 编号 | 需求 |
| --- | --- |
| **NFR-A1** | 任何输出（节点、claim、uncovered、查询结果、验证结论）都须能回指到具体来源 chunk 与原文 span。 |
| **NFR-A2** | 每次抽取/验证运行须记录 `ontology_version`、模型与提示模板版本、schema 版本、commit，以保证可复现。 |
| **NFR-A3** | 求解器 assertion 须保留到图断言与原文的映射表，作为可独立检视的制品。 |

### 3.4 可演化性与可替换性

| 编号 | 需求 |
| --- | --- |
| **NFR-E1** | 存储、求解器、模型须为**可替换实现基线**，不得让其特性污染抽取合同与 IR 语义。 |
| **NFR-E2** | 本体须可版本化演化；新增标签/谓词须走 schema 变更流程，并保持旧版本数据可读。 |
| **NFR-E3** | 本体须同时服务「分析可读」与「可编译」两个目的；对二者要求冲突之处须显式记录（见 §6 开放问题）。 |

### 3.5 安全与合规

| 编号 | 需求 |
| --- | --- |
| **NFR-S1** | 仓库内不得出现任何密钥、凭据、`.env` 内容或私有策划文档原文。配置示例只允许占位值。 |
| **NFR-S2** | 命名空间字段（`game_id`/`system_id`）**不是**安全边界，不得用于访问控制。 |
| **NFR-S3** | 依赖许可证（尤其图数据库的开源/商业许可）须在引入前经法务按实际交付方式确认；本设计草案不替代法务意见。 |
| **NFR-S4** | 用于评测的公开数据集，其代码许可不自动覆盖数据、模型权重与商业输入，须逐项确认。 |

## 4. 接口需求与数据需求

### 4.1 接口需求（详见 `docs/api/01-interface-contract.md`）

| 编号 | 需求 |
| --- | --- |
| **IR-1** | 所有输入输出须为带版本的 JSON 结构；顶层须含 `contract_version` 或 `ontology_version`。 |
| **IR-2** | 统一返回信封须含 `status`、`result`、`diagnostics`，`diagnostics` 携带非致命问题（`uncovered`、警告、拒绝原因）。 |
| **IR-3** | 错误码须分层：请求错误（4xx 语义）、契约违规（schema/本体校验失败）、能力缺失（方言不支持）、资源与超时、内部错误。 |
| **IR-4** | 版本管理须区分：契约版本、本体版本、IR 版本、schema 版本，四者可独立演进但须记录兼容矩阵。 |
| **IR-5** | 长耗时任务（批量抽取、验证）须支持异步提交与状态查询，或明确声明为同步阻塞并给出超时语义。 |

### 4.2 数据需求

| 编号 | 需求 |
| --- | --- |
| **DR-1** | 输入数据须登记来源：文档标识、chunk 边界、切分版本。切分方式变化须被视为一次版本事件。 |
| **DR-2** | 节点 `properties` 只允许原文明示的 `kind`、`code`、`tier_raw`；任意数值状态须由 `Attribute` 节点 + `HAS_ATTRIBUTE` 表达。 |
| **DR-3** | 单位须保留原文；不建立隐式单位换算表作为默认行为。 |
| **DR-4** | 概率与权重须分开存储：`weight` 不得被归一化为概率；`probability` 仅在可解析到 0–1 时附 `value`。 |
| **DR-5** | 时间语义须区分真实时间、游戏世界时间、叙事时间与协调时间；不得统一压成一个整数计数器。 |
| **DR-6** | 评测集须自建 gold set，不得仅依赖 LLM-as-a-judge；人工盲评与 judge 互换为必要环节。 |

## 5. 验收与度量

### 5.1 抽取层指标

| 指标 | 说明 |
| --- | --- |
| edge/claim precision、recall | 分层报告，不以单一 F1 代替 |
| 证据覆盖率 | `quote == chunk[start:end]` 比例，**目标 100%，硬门槛** |
| `unknown`/`uncovered` 拒绝 precision、recall | 不得只奖励召回 |
| domain/range 违反率 | **目标 0** |
| 实体重复率、图级冲突率 | 反映保守性与一致性 |
| `certainty` 四态 macro-F1 | 检验语气识别 |
| 多次采样一致率 | 稳定性 |
| P50/P95 延迟与 token 成本 | 附输入规模与模型版本 |

### 5.2 验证层指标

| 指标 | 说明 |
| --- | --- |
| solver 可编译率 | 有多少 claim 可进入形式化 |
| 反例可回溯率 | SMT assertion → 图断言 → 原文 span，**目标 100%** |
| 结果协议分类统计 | `proved`/`counterexample`/`bounded-no-counterexample`/`unknown`/`not-modeled` 各自占比 |
| 假反例率 | 过近似产生的假阳性比例 |
| 真实反例回放成功率 | 反例能否在仿真/规则路径上复现 |
| 分层性能与内存 | 按理论片段与状态规模报告 P50/P95/P99 |

### 5.3 报告纪律

- 抽取层与验证层指标**必须分别报告**，不得只给一个最终 QA 分数。
- 必须报告未知项与不变量映射（identity mapping），不得只报成功样本。
- 必须固定 commit、模型版本、schema 版本与 benchmark 配置。

## 6. MVP 范围

### 6.1 范围内（In Scope）

| # | 能力 |
| --- | --- |
| 1 | 单游戏、单子系统的 chunk 级本体受限抽取，输出符合抽取合同 |
| 2 | 确定性 validator（白名单、domain/range、证据连续性、限定值、certainty） |
| 3 | 抽取合同的两种物理投影（关系属性 / 独立 `Assertion` 节点），语义一致 |
| 4 | 确定性断言 ID 生成与版本修订（`supersedes`，冲突并存） |
| 5 | 两步路由（意图/槽位 → schema-aware 编译）的最小实现，支持一个方言后端 |
| 6 | D1/D2/D3 三类检查的**最小可运行**版本：图算法 + 区间过近似快筛 + 有界 SMT 精化 |
| 7 | 多结果协议与 assertion→claim→evidence 回映射 |
| 8 | 版本快照 + diff + 三类兼容性报告 |
| 9 | 评测脚本与自建 gold set 骨架，分层报告指标 |

### 6.2 范围外（Out of Scope，本 MVP 不做）

| # | 不做的事 | 理由 |
| --- | --- | --- |
| 1 | 跨文档实体对齐（`entity_link` 自动化合并） | 需要候选匹配 + 人工审核流程；本体已将其列为 planned |
| 2 | 端侧 SLM 微调 | 未训练基线的准确率不可外推；先建立评测基线再决定 |
| 3 | 多方言全量支持 | 先一个后端 + 能力探测，避免过早抽象 |
| 4 | 无界证明（完整 CHC / 随机博弈求解） | 属研究阶段；MVP 只做有界 + 抽象 |
| 5 | 「可玩性」「趣味性」的形式化证明 | 不可形式证明，只能验证明确代理指标 |
| 6 | 高并发写入的 SLA 承诺 | 缺少数据规模与硬件时无法诚实承诺 |
| 7 | 大规模商业游戏的可扩展性结论 | 公开案例不足以支撑 |
| 8 | 多 agent 抽取/验证编排 | 可能重复调用、相互确认错误；需独立证据才可启用 |
| 9 | 论文级 novelty 声明 | 需第二轮系统综述与专利排查 |

### 6.3 明确的风险接受

MVP 接受以下已知风险，并**显式**在设计中保留其暴露面（而非隐藏）：

- **R-a** 自然语言编译正确性是最高风险环节，MVP 不能消除它，只能通过三分编译与回映射把它外化。
- **R-b** 证据蕴含（quote 是否支持 claim）不可完全自动化；MVP 保留人工复核入口，并把它列为一等未知项。
- **R-c** 求解器性能不可按约束条数外推；MVP 只报实测曲线，不报推导值。
- **R-d** 本体计数不一致（设计文档称 25 个关系类型，表格逐项数为 24）须在本 MVP 内解决，见 `05-graph-schema-design.md` 与 `99-design-decisions-and-open-questions.md`。
