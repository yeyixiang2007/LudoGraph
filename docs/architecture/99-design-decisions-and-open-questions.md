# 设计决策与开放问题（对抗性自审）

- **状态：** v1 设计草案，必须在实现前接受独立评审。
- **目的：** 不为设计制造“已证明正确”的假象，而是把可攻击的决策、拒绝理由、翻转边界和未知项集中公开。
- **关联 ADR：** `docs/adr/0001`–`0010`。本表是 ADR 的评审索引，不取代 ADR 正文。

## 2. 已知自我怀疑清单

以下不是“风险已经解决”的清单，而是设计者认为最容易被独立审查击穿的八个点。每项必须保留「攻击角度 + 初步辩护 + 尚未确定的部分」。

### S1. 两步 NL2Cypher 是否真的优于端到端？

- **攻击角度：** 公开 benchmark 主要测端到端 Text2Cypher，并不能证明 Intent 路由减少错误；额外的路由步骤可能叠加错误、损失复杂问题召回。
- **初步辩护：** 分层方案至少让 scope、能力探测、拒答和参数化可以被确定性测试；这支撑可审计性和安全性，不等于支撑准确率优越性。
- **尚未确定的部分：** 尚无在 LudoGraph schema、同一问题集、同一模型/硬件上对等比较两种方案的执行准确率、拒绝率、尾延迟和 provenance 完整率。

### S2. Assertion 节点的语义收益是否值得额外查询跳数？

- **攻击角度：** 一跳查询是图数据库的核心优势；每次经过 Assertion 可能损害性能、查询复杂度和使用体验，物化投影又带来双写一致性。
- **初步辩护：** 当前问题明确要求冲突并存、来源、修订和回指，直接覆盖写无法满足；规范存储和热点投影分离是可审计性的直接实现。
- **尚未确定的部分：** 真实数据规模和查询分布下，Assertion 形态、直接边和混合视图的 p95/p99、写放大和重建成本尚未测量。

### S3. 过近似/欠近似三分是否足以防止错误证明？

- **攻击角度：** “过近似证明安全”依赖编译保持性证明；MVP 只有工程约定而没有形式定理，可能把错误模型的 UNSAT 包装成 proved。
- **初步辩护：** 设计明确要求 source map、assumptions、近似方向和 `not-modeled`，并禁止把有界 UNSAT 当全局安全；这些是暴露风险的机制。
- **尚未确定的部分：** 哪个受限规则子语言能先证明 soundness、每类 qualifier 的保持条件是什么、人工审核如何审计编译器本身，均未定稿。

### S4. 三类检测是否覆盖了实际最有价值的问题？

- **攻击角度：** D1/D2/D3 是 README 既定目标，但服务型游戏的概率尾部、版本迁移、策略博弈和时间语义可能比静态三类更重要；MVP 可能验证了容易的代理问题。
- **初步辩护：** 这三类能形成最小可运行验证闭环，并通过 Rule IR 为后续扩展保留接口；文档明确不把它们称为完整可玩性验证。
- **尚未确定的部分：** 目标用户实际优先级、真实缺陷分布和三类检查的业务收益尚未由案例或线上数据验证。

### S5. 17 标签/24 谓词是太严格还是太宽？

- **攻击角度：** 严格白名单会把重要机制大量送入 uncovered；`Concept`、`Effect`、`Condition` 的边界仍可能产生标注分歧，开放世界需求可能不适配。
- **初步辩护：** 叶子标签和 domain/range 提高可审计性；`Concept` 明确不能作未知类型兜底；uncovered 让本体缺口可计量而非静默污染。
- **尚未确定的部分：** 17 标签的跨玩法覆盖率、uncovered recall、扩展一个标签带来的精度/召回变化，以及标注者一致率尚未测量；24/25 计数也需权威文档最终裁决。

### S6. 连续 quote 是否被过度当成证据正确性？

- **攻击角度：** `quote == chunk[start:end]` 只证明位置和连续性，不证明它蕴含 claim 的方向、否定、条件和数量；硬门槛可能给人虚假安全感。
- **初步辩护：** 设计明确写出连续性不等于蕴含，并保留人工/NLI 审核；把能由代码确定的边界先硬化，优于让模型自证。
- **尚未确定的部分：** 证据蕴含的标注协议、人工成本、NLI 误报/漏报和何时降 certainty/转 uncovered 尚未定稿。

### S7. 单机 MVP 的“可复现”会不会遮蔽生产约束？

- **攻击角度：** 单机固定环境不能代表多租户隔离、故障恢复、高并发写入、网络延迟、模型 provider 差异；从 MVP 迁移到生产可能需要重写。
- **初步辩护：** 当前工作是 MVP 设计，不承诺生产 SLA；adapter、统一合同、异步任务、审计和备份接口刻意为扩展保留边界。
- **尚未确定的部分：** 真实容量模型、数据保留/删除政策、租户安全模型、队列和高可用架构尚未设计，也不应被本稿隐含承诺。

### S8. “有界验证 + provenance”是否会让用户误读为证明？

- **攻击角度：** 用户很可能把 `bounded-no-counterexample(k)`、过近似结果或 `explicit` claim 理解成“规则已证明安全”，尤其是在 UI 或摘要层。
- **初步辩护：** 结果枚举、assumptions、边界和禁止性文案已被放入接口、里程碑和工程门禁；未知不能映射为通过。
- **尚未确定的部分：** 面向策划者的最终解释文本、可视化、培训和误读率尚未做用户研究；不能仅靠枚举命名假定理解正确。

## 3. 开放问题（需要人类/评审裁决）

1. **第 25 个关系是否存在？** 权威数据模型文档目前表格为 24 项；若确实需要第 25 项，名称、domain/range、限定值和迁移策略是什么？
2. **MVP 的权威图后端是哪一个？** Neo4j 兼容基线的许可证、部署方式和真实负载 PoC 是否满足项目交付约束？
3. **Assertion 节点与直接边投影的读写比例、p95/p99 目标是什么？** 没有数据规模与查询分布，无法选择物化策略。
4. **哪些 claim certainty 可以参与哪些验证性质？** 请确认 `possible`、`planned`、`negated` 的业务语义和是否允许分支验证。
5. **MVP 的开放世界/闭世界默认是什么？** 不同选择会改变“未提及”与“禁止”的含义。
6. **时间、概率、权重、随机掉落的最小支持子集是什么？** 在缺字段时应拒绝到什么粒度？
7. **三类兼容性报告的判定标准是什么？** “资源价值不下降”“目标仍可达”“旧存档可继续”需要业务定义，而不是技术团队自行猜测。
8. **证据蕴含人工审核的责任主体和通过阈值是什么？** 连续 span 硬门槛不能替代该裁决。
9. **MVP 性能测试的固定硬件、数据规模、并发和超时预算是什么？** 在此之前所有快路径数字只能是待实测目标。
10. **公开 fixture 是否可以代表目标策划文档分布？** 若不能，gold set 如何取得授权、脱敏和标注？
11. **是否允许把设计意图以独立 claim 保存？** 若允许，必须怎样与规则事实、查询和验证严格隔离？
12. **版本兼容是否需要形式化精化关系，还是报告级 diff 足够？** 这决定 MVP 和后续研究边界。

## 4. 评审使用说明

评审者应优先攻击 S1、S2、S3、S5，而不是只检查文档是否完整：它们分别触及性能证据、存储语义、验证 soundness 和本体覆盖。任何被确认的反例都必须：

1. 更新相关 ADR 的状态、理由或推翻条件；
2. 更新需求、接口、模块或里程碑中的合同；
3. 增加可复现 fixture 或把事项明确转为 out-of-scope；
4. 保留修订记录，不删除原始决策理由。
